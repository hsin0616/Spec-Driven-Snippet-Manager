# Knowledge Snippet Manager v2.0 — 產品需求文件（PRD）

**文件版本：** v2.0 Draft  
**提出日期：** 2026-03-20  
**需求提出方：** 產品管理團隊

## 背景說明

Knowledge Snippet Manager v1.0 上線後，我們收到了來自早期使用者（學生、研究人員）的正向回饋，核心的新增、搜尋、標籤過濾功能已能滿足日常筆記需求。然而，隨著使用者的 snippet 數量逐漸增加，幾個痛點開始浮現：

1. **Snippet 建立後無法修正**：使用者記錯內容、打錯標籤後，唯一的選擇是刪除再重建，這會導致 ID 跳號，也讓使用者覺得資料不可靠。
2. **搜尋結果缺乏優先排序**：當使用者搜尋 `"Python"` 卻得到數十筆結果，全部以時間順序平排，很難快速找到最相關的那一筆。
3. **沒有辦法標記「重要的」snippet**：使用者希望能把某些筆記釘選或標記為重點，方便日後快速回顧，但目前的資料模型沒有任何支援此功能的入口。

v2.0 的目標是在**不破壞任何 v1.0 CLI 契約**的前提下，針對上述三個痛點逐步補齊功能。

## 需求列表

### 需求一：新增 `update` 指令（修改既有模組）

使用者應能對已存在的 snippet 進行部分欄位的更新，而不需要刪除後重建。

- 指令名稱為 `update`，必須接受 `--id` 作為必要參數，用以指定要更新的 snippet。
- `--title`、`--content`、`--tags` 三個欄位均為**選擇性參數**；使用者只需提供想要修改的欄位，未提供的欄位應保持原值不變。
- 更新成功後，該 snippet 的 `updated_at` 欄位必須更新為當下的時間戳記；`created_at` 與 `id` 不得被修改。
- 若指定 ID 不存在，行為應與 v1.0 的 `show` 及 `delete` 保持一致。
- 若使用者呼叫 `update --id 1` 但未提供任何欄位，程式應提示使用者至少需要指定一個要修改的欄位，而非靜默地做出無意義的更新。

> **刻意保留的模糊性：** 更新成功後的輸出格式，團隊尚未定案，請自行設計一個語意清楚、與 v1.0 輸出風格一致的格式，並在 SDD 中說明你的決策理由。

---

### 需求二：搜尋結果支援關聯性排序（修改既有模組）

目前 `search` 指令的結果以插入順序排列，使用者反映在結果數量多時難以判斷哪一筆最相關。

- `search` 指令應在現有行為基礎上，支援一個新的**選擇性參數** `--sort`。
- 當使用者未提供 `--sort` 時，行為應與 v1.0 完全相同（插入順序），以確保向下相容。
- 當使用者指定 `--sort relevance` 時，搜尋結果應依據關聯性進行排序，關聯性較高的 snippet 排在前面。
- 關聯性的定義由學生自行設計，但必須在 SDD 中以文字說明你的評分邏輯，例如：標題命中是否權重高於內容命中？多次出現是否加分？

> **刻意保留的模糊性：** 關聯性評分演算法的細節不做規定，我們期待你提出一個可解釋、可維護的方案，而非黑箱實作。

---

### 需求三：snippet 加星號（全新功能）

使用者希望能將特定 snippet 標記為「已加星號（starred）」，以便快速識別重點筆記。

- 新增一個 `star` 指令，接受 `--id` 作為必要參數，對指定 snippet 執行「加星號」或「取消星號」的**切換（toggle）**操作。
- 已加星號的 snippet 在 `list` 指令的輸出中，必須有可辨識的視覺標記，讓使用者一眼能區分有星號與無星號的條目。
- 新增一個 `starred` 指令，專門列出所有已加星號的 snippet，輸出格式應與 `list` 一致。
- 「已加星號」的狀態必須持久化儲存，重新執行程式後狀態不得遺失。
- `starred` 的狀態應以適當的方式儲存在現有的資料模型中；v1.0 資料模型中預留的 `metadata` 欄位是一個可以考慮的位置，但不強制要求。

> **刻意保留的模糊性：** 若使用者對一個不存在的 ID 執行 `star`，錯誤處理行為請自行決定，並與 v1.0 的整體錯誤處理風格保持一致。

---

### 需求四：`list` 指令支援排序選項（修改既有模組）

隨著 snippet 數量增加，使用者希望 `list` 的輸出結果可以按照不同條件排列，而非永遠以插入順序顯示。

- `list` 指令應新增一個選擇性參數 `--sort`，可接受的值至少包含：`created`（依建立時間，預設行為）與 `updated`（依最後更新時間，最新的排前面）。
- 當 `--sort` 未提供時，行為必須與 v1.0 的 `list` 完全相同，以保持向下相容。
- 若使用者傳入不支援的排序值，程式應給予明確的錯誤提示，而非靜默地使用預設值或崩潰。

## 驗收標準

以下標準以使用者可觀察的行為描述，不涉及實作細節：

1. **`update` 指令可正常運作**：執行 `update --id 1 --title "新標題"` 後，再執行 `show --id 1`，輸出中的 `Title` 應已更新為新標題，`updated_at` 應晚於 `created_at`，且 `Content` 與 `Tags` 保持原值。

2. **`update` 無欄位時不靜默執行**：執行 `update --id 1` 而不帶任何欄位時，程式應輸出提示訊息並以非零 exit code 結束，不應對資料做任何修改。

3. **`search --sort relevance` 可改變結果順序**：在有多筆 snippet 的情況下，執行帶有 `--sort relevance` 的搜尋，結果順序應與不帶 `--sort` 的結果有所差異（當確實存在不同關聯性分數時），且最相關的結果排在第一筆。

4. **`star` 切換行為正確**：對同一 `--id` 連續執行兩次 `star`，第一次執行後 `list` 輸出中應出現星號標記；第二次執行後標記應消失。重新啟動程式後，星號狀態仍應保留。

5. **`starred` 正確篩選**：執行 `starred` 後，輸出中只應包含已加星號的 snippet，且格式與 `list` 一致。

6. **`list --sort updated` 可依更新時間排序**：在有多筆 snippet 且其中部分已被 `update` 更新的情況下，執行 `list --sort updated`，最近被修改的 snippet 應排在最前面。

7. **v1.0 所有原有指令行為不受影響**：v1.0 測試案例中的所有指令（`add`、`list`、`show`、`search`、`filter`、`delete`）在不帶任何新增選擇性參數的情況下，輸出與行為應與 v1.0 定義完全一致。
